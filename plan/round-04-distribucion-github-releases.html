Lo que establece el repositorio

Hechos observados que restringen esta ronda de planificación.

El canal tradicional funciona de extremo a extremo

Velopack 1.2.0 empaqueta la publicación self-contained win-x64 en AIVitalsApp-win-x64-Setup.exe (113,7 MB) más el paquete completo de actualización (109,5 MB), y verifica que VelopackApp.Run() se ejecuta en el Main propio de la aplicación.

  • scripts/pack-release.ps1
  • https://docs.velopack.io/

El CHANGELOG ya tiene el formato que necesita el workflow

CHANGELOG.md sigue Keep a Changelog con encabezados '## <versión> - <fecha>', así que una sección por versión basta para generar las notas sin escribirlas dos veces.

  • CHANGELOG.md

El repositorio es público y con licencia MIT

github.com/AlexAdiaconitei/ai-vitals es público, de modo que el cliente puede leer las publicaciones sin token y el updater no necesita ningún secreto.

  • https://github.com/AlexAdiaconitei/ai-vitals

El bridge de Claude Code guardaba una ruta versionada

ClaudeCodeStatusLineInstaller escribe la ruta absoluta del helper en ~/.claude/settings.json. Dentro del árbol que Velopack reemplaza, una actualización podía chocar con el helper en ejecución y una desinstalación dejaba a Claude Code invocando un ejecutable inexistente.

  • src/AIVitals.Adapters.ClaudeCode/ClaudeCodeStatusLineInstaller.cs

No existía autoarranque ni versión visible

El código no escribía ninguna clave Run y ningún proyecto declaraba Version, por lo que todo se compilaba como 1.0.0 y la fase 06 partía de cero en ambos frentes.

  • Directory.Build.props
  • src/AIVitals.Platform.Windows

02 · Pipeline

El tag manda y el CHANGELOG es la fuente de las notas

release.yml es un workflow aparte de ci.yml, para que solo él tenga permiso de escritura sobre las publicaciones.

  1. Escribir la sección de la versión en CHANGELOG.md con el encabezado '## <versión> - <fecha>'.
  2. Ensayar con un tag de prelanzamiento, por ejemplo v0.1.1-beta.1, o lanzar el workflow a mano sin publicar.
  3. Publicar con git push del tag vX.Y.Z, que dispara verificación, empaquetado y publicación.
  4. El workflow extrae la sección del CHANGELOG y aborta antes de compilar si falta o está vacía.
  5. Se compila cada arquitectura, se descargan las publicaciones anteriores para generar deltas y se empaqueta con Velopack.
  6. Ambos canales suben a la misma publicación; después se sustituye el cuerpo por instalación, notas, tabla SHA256 y enlace de comparación.
Publicar una versión
git tag v0.1.0
git push origin v0.1.0

# Ensayo local del mismo empaquetado
dotnet tool install -g vpk --version 1.2.0
./scripts/extract-changelog-notes.ps1 -Version 0.1.0 -OutputPath artifacts/release-notes.md
./scripts/pack-release.ps1 -Version 0.1.0 -Runtime win-x64 -ReleaseNotesPath artifacts/release-notes.md

Reglas del workflow

  • La versión sale del tag y se propaga con -p:Version; Directory.Build.props deja 0.0.0-dev para que una compilación local se distinga de una instalada.
  • Un tag con guion, como v0.1.1-beta.1, se publica como prerelease y el updater estable no lo ofrece.
  • Las notas se generan solo en inglés, igual que el CHANGELOG y el README.
  • El disparo manual permite construir los instaladores sin publicar nada, y deja los artefactos en la ejecución del workflow.
03 · Actualizaciones

Comprobar y descargar solos; instalar solo cuando se pide

La comprobación es una llamada de red, así que se puede apagar; la instalación siempre exige una acción explícita.

Arranque y cada 24 hSe consulta el canal de la arquitectura, salvo que la comprobación automática esté desactivada.
→
Descarga en segundo planoVelopack baja el delta correspondiente sin interrumpir la sesión.
→
AvisoSección Acerca de y una entrada de bandeja que solo existe mientras hay una versión esperando.
→
Instalar y reiniciarLa aplicación libera monitor, bandeja y base de datos antes de ceder el control al actualizador.

Comportamiento observable

  • Un fallo de red en una comprobación automática es silencioso; solo una comprobación manual muestra el error.
  • Una copia no instalada por el instalador declara el estado como no soportado y oculta las acciones de actualización.
  • La entrada de bandeja de actualización no compite con el 'Actualizar' que refresca los datos de proveedor.
  • Las preferencias de actualización e inicio con Windows viven en preferences.json con esquema 2; un archivo de esquema 1 se migra conservando sus valores.

Por qué el bridge se mudó

Claude Code ejecuta el helper cada 30 segundos y Windows no puede sobrescribir un ejecutable en uso. Con el helper dentro del directorio que Velopack reemplaza, una actualización podía quedar a medias; fuera de él, un refresco fallido solo significa que el bridge sigue en la versión anterior hasta el siguiente arranque.

06 · Cambios

Diferencias respecto a la ronda 03

La fase 06 planteada en la ronda anterior prometía más de lo que esta implementación entrega, y conviene que el dossier lo diga.

Se reduce

  • Doble canal EXE + MSIX/Store pasa a canal único de GitHub Releases.
  • Release notes bilingües pasan a inglés, coherente con CHANGELOG y README.
  • SBOM, checksums firmados y escaneo de dependencias salen del pipeline; los checksums se publican, el resto queda manual.
  • La verificación en VM limpia deja de ser un gate automático y pasa a lista firmada.

Se añade

  • Autoarranque opt-in, que la ronda 03 daba por hecho y no existía en el código.
  • Sección Acerca de con versión, canal y control de las actualizaciones.
  • Reubicación del helper de Claude Code para que la actualización no choque con un proceso en marcha.
  • Migración de esquema de preferencias en vez de descartar el archivo anterior.
Sin proyecto AIVitals.Packaging

La estructura objetivo de la ronda 01 reservaba un proyecto de empaquetado. Velopack se usa por CLI, así que el empaquetado vive en scripts/pack-release.ps1 y en el workflow, sin un csproj que no compilaría nada.

Hilos sueltos

Incertidumbre contabilizada

Los hilos abiertos requieren disposición; los bloqueados siguen visibles hasta resolver su dependencia.

06

Firma de código Authenticode

material

Las publicaciones salen sin firmar, así que SmartScreen advierte en la primera ejecución. El paso de firma existe en el workflow y solo se activa si aparece el secret WINDOWS_SIGN_PARAMS.

Reactivación · Al contratar certificado o al aprobarse Trusted Signing: añadir el secret, sin cambios de código.

07

Canal MSIX y Microsoft Store

watch

La ronda 03 planteaba dos canales simultáneos. Se reduce a uno para evitar doble updater, identidad de paquete, cuenta de Partner Center y revisión de Store.

Reactivación · Cuando el canal de GitHub Releases acumule instalaciones estables y se quiera distribución de Store.
